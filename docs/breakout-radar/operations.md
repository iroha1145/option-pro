# 突破雷达运维

## 运行方式

突破雷达由统一`worker`中的`breakout`任务管理，不再单独启动常驻进程。功能状态与调度间隔写在`config/personal.toml`：

```toml
[features]
breakout_enabled = true

[breakout]
regular_seconds = 300
premarket_seconds = 600
closed_seconds = 1800
range_persistence_mode = "shadow"
```

查看统一工作进程：

```bash
./scripts/compose.sh exec -T worker python -m app.worker --healthcheck
```

健康结果中的`breakout`条目记录定时扫描的运行、暂停、禁用或降级状态；`breakout_refresh`单独记录 Owner 手动扫描。统一健康清单共十项，其中`public_home`只定时保存公共首页数据；部署检查只读取记录，不启动扫描。

## 调度

- 盘前默认 600 秒；
- 正常交易时段默认 300 秒；
- 盘后和休市默认 1800 秒；
- 休市时进入中性暂停，不请求候选数据源，也不登记失败扫描；
- 数据源故障采用有界退避，其他后台任务继续运行。

## 状态判断

`/api/breakouts/status`显示最近完成扫描、数据源健康、数据库状态和区间强势持续度模式。`/ready`不依赖突破数据库或外部数据源，突破异常不能通过修改后端就绪结果掩盖。

有效空结果、陈旧快照和数据源不可用是三种不同状态：

- 数据源正常返回零候选时，才发布有效空快照；
- 合格旧快照仍在保留期内时，标记陈旧并继续展示；
- 没有可用快照且数据源失败时，本轮降级，不覆盖上一次成功结果。

## 数据库故障

数据库忙时检查是否存在超长写事务；网络请求不得持有写锁。轻量数据库预写日志（SQLite WAL）增长时，检查长读连接和磁盘余量，优先使用被动检查点，不在活跃读取期间强制截断。

数据库损坏或权限异常时，先保留文件副本，停止统一工作进程，再从经过摘要、完整性和外键检查的备份恢复。不要在工作进程运行时替换数据库文件。

## 容器边界

`backend`与`worker`使用同一镜像和`optix-data`数据卷，根文件系统只读，以非根用户运行。`worker`不暴露端口。机器网络边界与统一`DATA_DIR`保存在`machine.env`，五个服务端密钥保存在`secrets.env`。突破数据库路径由`DATA_DIR`派生，不再单独配置。日志不得输出密钥、请求头、新闻正文或原始模型响应。

真实数据源扫描不是部署健康检查。持续集成使用关闭突破任务的容器配置；算法路径通过本地夹具和模拟传输验证。

## 手动扫描

Owner 在页面发起的突破或强度刷新会写入持久化工作请求，由`worker`执行并记录结果。重复点击会受冷却、幂等与工作进程状态约束，不会把真实扫描偽装成部署健康检查。
